# X14: high-loss file transfer — design for review

**Proposal only;** base R3 `3c48d7e7`. Target browser↔device verified goodput ≥10× the measured current baseline (historically ≈0.3 Mbit/s) at 230 ms RTT and 3% loss, without compromising access, integrity, remote control or fairness. No implementation or network experiments until Claude approves this design.

**Current state.** One browser `RTCPeerConnection` carries a reliable, ordered `files` DataChannel (`ui/src/composables/useRemoteControl.ts`, `agents/meshharbord/src/{peer,files}.rs`). Binary frames are raw bytes without transfer ID/offset; one upload and one download can run concurrently, but a single file cannot be striped safely. Upload resume truncates to a 256 KiB boundary; the reserved hash prefix is ignored, and completion checks size rather than a content hash. Progress acknowledgments do not guarantee disk durability; download length mismatches are not currently rejected. FILES permission, session lifecycle, OS identity, path restrictions and secret-file denial are security boundaries. The CLI has no native file-copy command: `scp`/`sftp` use `mh proxy`; SFTP rejects shared-device and one-command grants. The existing QUIC tunnel is not file authorization; pinned quinn supports BBR, but this project currently uses CUBIC.

**Browser proposal.** A rough loss-based throughput estimate suggests 1–4 ordinary associations may be far short of the 10× target; it is not a measured bound. Negotiate a new capability over the authorized control session and stripe **one file** across 1–4 independently authenticated `RTCPeerConnection`s. Multiple DataChannels inside one association share its congestion window ([RFC 8831 §6.1](https://www.rfc-editor.org/rfc/rfc8831.html#section-6.1)). A second ordinary offer currently closes the first peer, while the server admits only one consented offer: introduce bounded child-transport IDs and signaling with fresh DTLS identity proofs bound to the original session, controller, FILES grant and transfer. Do not reuse the old session ID, replace the remote-control peer, or bypass consent. Bind child lifetimes to revocation/session close; preserve old peers via capability-gated fallback.

**Separate directions.** For **download (device→browser)**, evaluate a bandwidth/RTT-based pacing and congestion controller in our vendored SCTP sender, combined with 1–4 file-only associations. Gate it per authorized session, default off, and retain the existing controller as an immediate fallback; never alter the association carrying interactive control. Random loss cannot reliably be distinguished from congestion: do not simply suppress all loss response, and reject the experiment if its fairness or resource gates fail. For **upload (browser→device)** Chrome controls the SCTP sender, so measure the 10× target separately while evaluating 1–4 associations; more require a separately reviewed resource ceiling. Evaluate application FEC only after protocol feasibility is demonstrated. Reliable ordered SCTP can block repaired data behind retransmission and FEC does not remove its congestion control; a FEC experiment must explicitly specify ordering/reliability, overhead, acknowledgments and integrity. If upload cannot reach 10× within the safety limits, report its measured ceiling rather than claim success.

Introduce framed transfer ID, offset/length and chunk hash; verify chunks, reject overlap/mismatched peers, and use a session-wide atomic claim for each partial file so concurrent resumes cannot truncate or write the same ID. Persist only verified/durable ranges for resume; validate the final whole-file hash before atomic publication. Bound disk, buffers and partial lifetime; preserve filesystem identity, paths and cancellation. Start at one association, increase only while goodput improves and limits hold; striping is a hypothesis, not a promised speedup.

**Device↔device proposal.** Evaluate a separate file protocol on a dedicated connection using existing QUIC and peer authentication; compare pinned quinn CUBIC vs BBR as a reversible per-transfer experiment. Multiple streams on one QUIC connection still share congestion control. Enforce file-specific OS identity, authorization and path restrictions independently of tunnel authentication, or reject; retain SSH/SFTP as fallback and do not change shared tunnel or overlay defaults. QUIC tuning does not automatically accelerate browser SCTP or SSH traffic.

**Fairness and TURN.** One session-wide scheduler limits aggregate in-flight/queued bytes and parallel connections, backs off on loss/RTT/interactive congestion, and obeys existing server quotas. Proposed ceilings: ≤4 additional TURN allocations per endpoint per transfer; relay file-direction egress ≤2× verified file bytes + 8 MiB per completed transfer. Record allocations, egress and bandwidth; lower existing quotas take precedence. Failed negotiation or resource pressure falls back to one connection.

**Acceptance.** Use isolated endpoints and traffic shaping, not an active user network. Record exact revisions, carrier (direct/TURN), capacity, MTU, CPU/disk, queue and random seed; shape **230 ms total RTT and 3% independent loss each direction**, plus no-loss control. Alternate ≥3 identical baseline/candidate trials per direction and designated route; report each verified goodput, completion time, failures, setup cost, retransmissions, CPU/memory and TURN usage. For download, compare the existing controller and experimental controller at 1–4 associations; for upload report separately the browser-limited result and any FEC cost. A direction passes throughput only when median verified goodput is ≥10× its measured baseline and every completed file has the correct hash; otherwise report the ratio and limits. Test simultaneous bulk traffic and interactive remote control: competing-flow median ≥80% of its median with the old single-connection transfer, and input-to-response p95 ≤max(1.25× that baseline, baseline + 50 ms). Test interruption/restart, corruption/overlap, simultaneous resume ownership, revoked/unauthorized sessions, cleanup, fallback and unchanged remote-control connection. If any correctness, fairness or resource gate fails, reject or reduce concurrency even if the throughput target passes.

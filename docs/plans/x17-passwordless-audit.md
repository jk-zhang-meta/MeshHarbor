# X17: passwordless access audit and RDP design

**Status:** design approved by Claude with the user clarification relayed in the handoff, based on R3 `3c48d7e7`. Initial configuration or authorization may require one manual confirmation or entry; repeated use must not require another password or key entry. This is a user-experience objective, not permission to skip authentication, consent, MFA or target OS policy. No implementation or authentication tests have been performed. The goal covers MeshHarbor registration, sign-in, enrollment and features; external identity providers, operating systems and third-party apps retain their own policies and may need explicit setup or an unsupported result rather than a false passwordless promise.

## Current entry points

| Flow | Current behavior / remaining work |
| --- | --- |
| Account registration, login and approval-status lookup | Registration/login ask for an account password; approval lookup requires password proof (`ui/src/views/auth/{RegisterView,LoginView}.vue`, `crates/api/src/routes/{auth,account_approval}.rs`). Approved OAuth providers may authenticate without a MeshHarbor password, but their own MFA/password prompts are outside this product's control. No complete passkey/recovery flow was established in this audit. |
| Enrollment | `mh enroll --token` and desktop onboarding require a token. Replace manual token copying with a short-lived, device-bound, one-time approval/QR or deep link, preserving owner approval and replay/expiry checks; enrollment tokens are authorization material even if they are not passwords. |
| Same-organization SSH and exec | `mh ssh` already obtains a single-use SSH grant and pins the host key; `mh exec` uses daemon identity and separate authorization gates. SSH generates a temporary key on disk with restrictive Unix permissions and best-effort cleanup; Windows ACL behavior requires verification. Exec commands/results pass through the control server, so do not describe exec as end-to-end secret from that server. |
| Shared SSH / stock SCP | `share-ssh --login` asks for the account password; token-file mode avoids the prompt but expects an existing general account token. Design browser-mediated, one-time device authorization yielding a narrowly scoped, short-lived, revocable share grant with MFA proof, never a general-purpose token file. Standard SSH/SCP/SFTP via `mh proxy` still use external SSH authentication; a native authorized file wrapper would be new work. Preserve owner-selected OS identity, grant expiry/revocation and the existing shared-SSH SFTP/forwarding denials. |
| External device-code remote control | The code flow currently requires a separate device access password and uses OPAQUE (`ui/src/views/remote/ConnectView.vue`). Offer an owner-approved, short-lived and device/session-bound possession approval instead; preserve origin checks, consent, FILES/remote-control permissions, revocation and rate limits. A connection code alone is not sufficient authorization. |
| Device sharing, file UI, chat | Existing account sessions and device/tenant/room grants provide access without a distinct feature password; keep their permission and consent checks. Device sharing can select an OS account, and selecting administrative access can grant real passwordless sudo: show and audit the privilege, do not silently expand it. |
| Remote lock screen / third-party applications | Remote keystrokes can reach a host login screen; MeshHarbor does not currently authenticate that OS session. Passwordless account/OS setup needs a supported OS credential or trust mechanism; never replay captured keystrokes, bypass a lock screen, or treat a MeshHarbor login as automatic authorization to every OS account. Applications' own authentication is outside the currently proven feature set. |
| RDP | No RDP client, gateway, `mstsc`/FreeRDP integration or Windows credential form was found. Existing loopback forwarding provides a byte path only; it does not authenticate NLA, verify the RDP host, decode RDP in the browser, or create an RDP session. |

## Proposed identity and RDP boundary

Use device-bound, phishing-resistant passkey/OS-backed identity plus existing MFA and explicit account recovery/approval for MeshHarbor account access; issue purpose-, device-, audience- and expiry-bound capabilities after successful authentication. Browser-to-native handoff must use a one-use challenge with explicit device confirmation, not a reusable account JWT, and must be replay-resistant, revocable, and redacted from logs/URLs. Fully unattended first registration and recovery without *any* trusted authenticator or human action is not established; define enrollment and recovery ceremonies before claiming complete coverage.

For RDP, first validate a **native Windows client path** through the authorized loopback tunnel, with target certificate/hostname and NLA identity bound to the actual device. Prefer existing Windows integrated Kerberos/Remote Credential Guard where the environment supports it; Microsoft requires Kerberos and a suitable AD/domain configuration, so this is not a universal solution ([Microsoft: Remote Credential Guard](https://learn.microsoft.com/en-us/windows/security/identity-protection/remote-credential-guard?tabs=intune)). Tunnel loopback addresses can break certificate name/SPN matching and must not be “fixed” by disabling verification. For non-domain targets, explore an explicitly provisioned OS-protected local credential or target-bound broker as a separate design: it may eliminate repeated entry, but needs an initial trustworthy provisioning/rotation/recovery mechanism and must respect target account policy. Do not pass credentials via command arguments, environment, temporary files, logs or untrusted server processes. A browser RDP gateway or FreeRDP adapter would be a separate feature requiring explicit trust, packaging and protocol validation; a raw TCP tunnel is not that feature.

For the RDP proposal apply the strict interpretation **the control server never receives or can decrypt the RDP secret**, including in memory; authorized endpoint/client processes may need plaintext transiently to authenticate and must use OS-backed storage and tight lifetime controls. Existing vault APIs do not return stored values to the operator, but the vault server can decrypt them and its write API receives plaintext (`crates/modules/vault/src/{lib,routes}.rs`); this is a different trust model and cannot satisfy the strict RDP boundary merely by hiding the API response. Do not alter or migrate existing vault data as part of this proposal.

## Acceptance

The inventory and RDP trust boundary have Claude's approval; each feature still needs a concrete reviewed implementation and exact first-use/recovery behavior. Before declaring a flow passwordless, test first enrollment, repeat access, expiry, logout, revocation, recovery and MFA; prove unauthorized device/controller/tenant, stale grant, replay and compromised-server attempts fail without widening existing privileges. Inspect logs, argv, URLs, crash/temp files and persistence using synthetic credentials only. For RDP, separately test supported domain and non-domain cases, target identity mismatch, NLA failure, tunnel lifecycle, credential rotation and host policy; unsupported configurations must fail clearly. Verify Windows temporary-key ACL/cleanup and native SFTP/exec distinctions rather than asserting them. No production identities, secret reads, deployment or auth weakening is authorized by this design.
